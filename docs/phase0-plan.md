## 0. 一页摘要

- **4 周回答四个问题**：整数宇宙能不能既逐位一致、又"像 Lenia"；鉴定和预览要多少算力；研究者愿不愿意参与定义问题；在一个最小探索器里，"发现那一刻"是否存在。
- **四条工作线**：A 外联与研究；B 规范与参考实现；C 最小探索器与试玩；D 决策与法务。
- **依赖外部的事先做**：第 1 周头几天，创始人只做三件事：定数据许可方向，发出研究简介和给 Chan 的许可请求，做商标初查。工程第 1 天开工，不等外联。
- **继续标准分两档**：8 项"必须"，不满足就不进入第一阶段；6 项"应当"，不满足要选定退路（第 6 节）。
- **第 4 周末开评审会**，创始人拍板：进入第一阶段、延长 1–2 周，或调整方向（第 9 节）。
- **宇宙规范在第 0 阶段只是草案**（v0.x），在第一阶段首条登记之前才冻结为 v1.0。参考实现规格的细节不单独成文，分别写进规范草案和本计划。
- **保持精简**：第 0 阶段只写第 11 节列出的文档，其余推迟，把时间留给原型和访谈。

### 1.2 不在范围内

- 第一阶段的任何功能：账户、图鉴、登记、鉴定服务、查重、评审队列、AI 普查、数据导出、周报。
- 冻结宇宙规范 v1.0。第 0 阶段只出草案。
- 参考实现的完整规格：Python 绑定、WGSL 精确路径、容器镜像归档、可复现构建，都属于第一阶段。WGSL 只在精度决策里估算影响（第 7 节）。
- 对外试玩、招募玩家、收集任何其他人的游戏行为数据。第 0 阶段只有创始人自己试玩。
- 对外发布任何来自 Chan 工作的物种数据，或"某个文献物种在 lenia-q16 下能否复现"的结果（第 5.3 节）。
- 美术、图版生成器、野外笔记、音频、多通道 Lenia、Flow-Lenia。
- Logo、社交账号等品牌资产。名称定下来之前不做。
- 团队、预算与资助计划。它是第一阶段开工前的文档，不在本计划内。

### 1.3 本计划对 GDD 的具体化

GDD 有几处说法要先变成可以检验的标准。下面是本计划的解释，创始人确认后记进决策日志。

| GDD 原文 | 本计划的解释 |
|---|---|
| "WASM 版和服务器原生版在 3 种平台上逐位一致"（§19.1） | 3 个原生平台，加 3 个桌面浏览器里的 WASM，共 6 个配置（第 4.1 节） |
| "整数参考实现能稳定复现 Orbium 等约 10 个经典物种"（§19.1） | 确定性（G1）加行为一致（G2）。已知的非柏拉图型物种允许行为不一致，但必须记录差异（第 6.3 节） |
| "确认文献物种的导入许可"（§19.1） | 回复不由我们控制。标准改为：收到书面答复，或者按[许可请求函](./outreach/chan-permission-request.en.md)第 6 节选定退路（G5） |
| "通过合作机构提交研究伦理审查申请"（§19.1） | 目前没有合作机构。标准改为：已提交，或者选定退路（S4） |
| "创始人自己玩一周"（§19.1、§21） | ≥ 5 次有日志的试玩（G8，第 8 节） |
| "16 位精度够不够用"（§14.2） | 按第 7 节的判定规则回答，结论写进决策日志 |

### 2.2 如果目前只有创始人

现状就是这样。原则是：**标准不变，时间和做法可以变。**

1. **A、D 两条线照常。** 它们本来就由创始人负责，而且依赖外部，越晚开始越吃亏。
2. **B 线三选一**，W1 第 1 天决定，写进决策日志：
   - 创始人自己写最小版本：直接求和、原生加 WASM、Orbium 加 3–4 个基准物种。NTT 和测量 M1、M2 推到延长期或第一阶段。
   - 找一位短期或兼职工程师。需要预算；合同要写清知识产权归属和开源许可（列入法律备忘）。外联材料里不提此人，除非对方同意。
   - B 线整体推迟，第 4 周的评审结论预期就是"延长"。
3. **C 线可以先用现成程序。** 试玩可以先用 Chan 以 MIT 许可开源的 Lenia 程序。它不是我们的探索器，结果只算方向信号，日志里写明用的是哪个程序。
4. **因为人手不够没做完的标准，评审结论是"延长"，不是"调整方向"。** "没做完"不等于"做了但不通过"，只有后者才是调整方向的依据。
5. 招聘不在第 0 阶段的交付里。单人启动时，创始人每周留出半天（暂定）找工程师，这段时间从外联和试玩里扣。

每周一开 30 分钟计划会（暂定），每周五更新第 6 节的记分卡。

### 3.1 第 1 周（W1）：先发出去，再开工

**头三天，创始人按这个顺序做**：

1. **第 1 天**：拍板数据许可方向；开始商标初查；读 Davis（2024）、Hudcová 等（2026）、Gupta（2026）的原文，核实研究简介里标 [verify] 的句子，核实不了的整句删掉。
2. **第 2 天**：研究简介定稿，填好占位符，放到一个能打开的链接上；从公开来源核实 Chan 的邮箱；**发出给 Chan 的许可请求**（单独发送）；开始逐个发出研究简介。

### 4.2 测试协议

1. **测试向量** = 规范草案版本 + 规则参数 + 初始状态的哈希 + 环面尺寸 + 步数。全部写进规范草案的附录。
2. **初始状态**：基准物种用整数版培养出的成体快照：从种子出发运行，直到质量稳定，再截取（第 5.3 节）。另加 2 个随机汤，由固定种子的整数伪随机数生成。随机汤是混沌的，任何一位的差异都会很快放大，所以是最严格的逐位测试。
3. **步数**：每个测试向量跑满 2000 个时间单位（§8.3），也就是 2000 × T 步。T = 10 时为 2 万步。
4. **环面**：默认 256×256（暂定）；R 较大的测试向量用 512×512（暂定）。
5. **哈希链**：每 256 步（§14.2(4)，暂定）对规范序列化后的状态取一次哈希，和上一个链值连起来。保存全部分段，不只保存链头，这样出现分歧时能定位到第一个不同的分段。
6. **构建**：所有配置用同一个代码提交。测试构建打开整数溢出检查，用来证明按设计不会溢出；普通发布构建也要跑，两者的哈希链必须相同。
7. **通过**：6 个配置上，全部测试向量的全部分段逐位相同。没有容差，没有例外。
8. **算法一致（S1）**：在 P1 上，直接求和版和 NTT 版对同一组测试向量给出相同的哈希链。
9. **出现分歧时**：找到第一个不同的分段，从那里逐步比对，直到找到原因。修好之后**全部**重跑，不只重跑出问题的配置。
10. **float64 对照**只在 P1 上跑。它不要求跨平台一致，只用来做第 6.3 节的行为对比。

### 4.3 逐位一致的前提（写进规范草案）

1. 精确路径里没有任何浮点运算，包括核权重和生长查找表的生成。
2. 不用 WASM 的 relaxed SIMD。这类指令允许不同实现给出不同结果。普通 SIMD 可以用。
3. 数值一律用定宽整数（u16、u32、u64）。不用 usize 存数值：它在 wasm32 上是 32 位，在 64 位原生平台上是 64 位。
4. 按设计不会溢出：核权重总和为 2^16、状态最大为 65535 时，Σw·A ≤ 2^16 × 65535 < 2^32。改用方案 B 时要重新证明（第 7 节）。
5. 取整规则写死：右移是向下取整；查找表生成里的每一处取整都写明方向。
6. 状态的规范序列化写死：行优先，小端字节序。
7. 结果不依赖哈希表的遍历顺序或线程调度。整数加法在不溢出时和求和顺序无关，所以多线程和 SIMD 求和不影响结果；但规范仍然写明求和的定义。

## 7. 精度决策点

### 7.1 问题在哪里

附录 A 的草案是：状态 16 位；核权重非负、总和为 2^16；势 U = (Σw·A) >> 16，用一个 u32 累加。正因为不超过 32 位，WebGPU 上才能写逐位精确的直接求和版（§14.2(2)）。精度可能在三处不够：

- **核权重**：总和固定为 2^16，平均每格约 2^16 / (πR²)。R = 13 时约 120，R = 50 时只有约 8。R 越大，量化的相对误差越大，核边缘的小权重会被取整成 0。
- **状态和增量**：状态的最小单位是 1/65535。T 越大，每步的增量 Δt·G 越小，小增量会被取整掉，接近平衡时的细微变化可能丢失。
- **生长查找表**：势的分辨率是 1/65536。σ = 0.015 时，生长函数的钟形（约 ±3σ）覆盖约 5900 个表项（估算）。估计够用，诊断时一并确认。

所以，"够不够用"的答案取决于规范 v1.0 允许的 R、T 范围，不是一个简单的是或否。

### 7.2 怎么诊断

1. **核误差扫描**（W1，不用跑模拟）：R 从 5 到 60（暂定），计算量化核和理想核之间的 L1 误差、各环的质量误差、被取整成 0 的格子比例。
2. **整数对 float64 的行为对比**（W2–W3）：见第 6.3 节。
3. **分离误差来源**（只对没通过 G2 的柏拉图型物种做）：在 float64 框架里每次只量化一处，看哪一处能重现失败：
   - 只量化核权重；
   - 只把状态每步量化到 16 位；
   - 只把生长函数换成整数查找表。
4. **试跑方案 B**（W3，只在原生版上）：如果误差来自核权重，就提高核权重的精度，看失败是否消失，同时测速度损失。

### 7.3 选项

| 方案 | 内容 | 代价 |
|---|---|---|
| A（现方案） | 16 位状态，核权重总和 2^16，u32 累加 | 没有额外代价；WGSL 精确路径简单 |
| B | 16 位状态，核权重总和提高到 2^24 或 2^32（暂定），64 位累加。原生和 WASM 有 64 位整数；WGSL 没有，要用两个 u32 模拟，就是 §14.2 说的"双 u32" | 附录 A 的移位和溢出证明要改；WGSL 精确路径变慢，慢多少要估算；原生和 WASM 也变慢，M1 要重测 |
| C | 保持 A，在规范 v1.0 里把 R、T 限制在 A 够用的范围内 | 离散化依赖测试（§8.3）往更大的 R、T 扩展时受限，柏拉图型的判定可能受影响；以后放宽要发新版规范 |
| D | 诊断指向状态量化，A、B、C 都解决不了 | 要改状态位数，相当于另一份规范（如 lenia-q24）。超出第 0 阶段的范围，提交评审会 |

### 7.4 判定规则（暂定）

- 柏拉图型基准物种全部通过 G2，并且在规范草案的 R 范围（加上离散化测试会用到的更大的 R）内，核的 L1 误差 ≤ 1%、各环质量误差 ≤ 2%（暂定）→ **选 A**。
- 失败来自核权重，或者核误差在上述 R 范围内超线 → 比较 **B** 和 **C**。限制之后的 R、T 范围仍能覆盖全部基准物种和 §8.3 离散化测试的需要，就选 C；否则选 B。
- 失败来自状态量化 → **D**，提交评审会，同时按第 9.4 节 G2 不通过处理。
- 失败来自查找表 → 修改查找表的生成规则（取整方式或索引精度），不需要 B。

### 7.5 时间与拍板

- 后端在 W3 末提出建议并附证据，写进决策日志草稿；创始人在 W4 评审会上拍板。
- **最晚在规范 v1.0 冻结之前定下。** 方案 B 会改附录 A 的公式和 §14.2(2) 的 WGSL 精确路径，冻结之后就不能改了。
- 第 0 阶段没有定下来时：第一阶段第 2 周（暂定）之前必须定，否则推迟首条登记。
- 选 B、C、D 中的任何一个，都要同步修订 GDD 附录 A 和 §14.2，必要时修订 §8.3，并在附录 D 留记录。
