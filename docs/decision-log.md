## 怎么用这份日志

1. **一条决定一个条目。** 编号从 D-001 起顺序分配，永不复用。条目不删除。
2. **状态只有四种：**

   | 状态 | 含义 |
   |---|---|
   | **提议** | 写好了选项和建议，还没拍板。建议只是建议，不能当作已经决定 |
   | **已采纳** | 拍板人已经确认。相关文档按它写 |
   | **已否决** | 讨论过，不采用。保留理由，免得以后重复讨论 |
   | **已替代** | 被后来的条目取代，写明"由 D-xxx 替代" |

3. **谁拍板。** 每条写一个拍板人，写的是角色（见 GDD §19.2）。目前到岗的只有创始人/制作人，所以眼下所有条目实际都由创始人拍板。技术条目写的是将来负责的工程角色：工程师到岗后，可以对还在"提议"状态的条目提出修改。顾问只提供意见，不拍板；目前还没有顾问（D-006）。
4. **怎么改已采纳的决定。** 不改原条目的正文。新增一条，写明"替代 D-xxx"和理由；原条目的状态改为"已替代（由 D-yyy 替代）"，其余内容保留。"提议"状态的条目可以直接修改。
5. **截止时间。** 第 0 阶段共 4 周，写作第 1 周…第 4 周（W1–W4），和[第 0 阶段执行计划](./phase0-plan.md)的周结构一致：

   | 周 | 这一周要拍板的决定 |
   |---|---|
   | 第 1 周（W1） | 外联、许可、商标检索、工具链 |
   | 第 2 周（W2） | 宇宙规范草案层面的选择 |
   | 第 3 周（W3） | 数值方案与 NTT |
   | 第 4 周（W4） | 第 0 阶段评审层面的决定 |

   更晚的写"第一阶段开始前""第一条登记之前"或"第二阶段开始前"。
6. **过了截止还没拍板。** 第 0 阶段每周末过一遍本日志。依赖它的工作可以先按建议做，并标"暂定"。但对外发出的文字和不可逆的动作，即发出许可请求、冻结宇宙规范、第一条登记、公开发布数据，必须等拍板之后。
7. **从 GDD 和其他文档链接到这里。** 每个条目前都有固定锚点，链接写作 `[D-018](./decision-log.md#d-018)`。条目里引用 GDD 时写章节号，例如 §8.5(1)。GDD 修订时，在附录 D 里注明对应的条目编号。
8. **暂定数值。** 凡是估计出来的数字都标"暂定"，并写明靠什么确认。

<a id="d-001"></a>
### D-001 优先权锚点：命名优先权以描述提交承诺为准

状态：**已采纳** · 日期：2026-10-20

**背景**：v0.1 里 §8.2 写"优先权的时间点以承诺哈希为准"，§14.5 的注释写"承诺哈希，决定优先权"，两处指的都是采集时的承诺；§8.5(1) 却写优先权以有效描述为准。两种说法互相冲突，登记状态机和承诺协议都没法写。

**选项**：采集承诺决定优先权 / 描述提交承诺决定优先权。

**决定及理由**：设两个承诺。**采集承诺**确定采集时间，只决定采集者的功劳；**描述提交承诺**确定描述提交的时间，决定命名优先权。时间都以服务器时间戳为准（§14.8），§14.5 的数据模型分成 `collection_commitment` 和 `description_commitment` 两个字段。理由是这样才和"命名权归第一个有效描述者"（§3.2(1)）一致：如果采集时间决定优先权，AI 普查的大量采集就会挡在人的描述前面，"采集"和"描述"的拆分就失去了意义。分成两个承诺之后，采集者和描述者的功劳各有一个可验证的时间。注意：本条以"命名权归第一个有效描述者"为前提，而这个前提本身是 §22(3)，创始人还没有明确确认（D-015）。

- **截止**：已定。还没定的细节：同一时间戳内两份描述怎么裁决、承诺具体对哪些内容取哈希，写进命名法规 v0，序列化见 D-026
- **拍板人**：创始人/制作人
- **影响的文档**：GDD §8.2、§8.5(1)、§14.5、§14.8；`naming-code-v0.md`；数据模型与导出格式；[研究者外联简介](./outreach/research-brief.en.md)
- **复审条件**：D-015 改为"第一个采集者"时，本条由新条目替代

<a id="d-002"></a>
### D-002 核与生长查找表由规范算法确定性生成；参数用定点编码

状态：**已采纳** · 日期：2026-10-20

**背景**：v0.1 把核权重和生长查找表写成可以事先冻结的表。可是参数是连续的，每个规则点的核和查找表都不同，不可能事先全部列出。

**选项**：冻结一批表 / 由规范规定生成算法。

**决定及理由**：宇宙规范规定由参数生成核权重和生长函数整数查找表的**确定性算法**，只用整数和定点运算；生成结果取哈希，写进条目（§14.5 的 `generated` 字段）；规则参数用规范定义的**定点编码**。这样任何人只凭规范和参数就能重新生成同样的表，并用哈希核对；某个实现生成错了，哈希马上对不上。具体用什么算法见 D-022，编码和格点见 D-024，哈希算法见 D-021。

- **截止**：已定
- **拍板人**：创始人/制作人
- **影响的文档**：GDD §5.4、§14.2(1)、§14.5、附录 A；`spec/lenia-q16-draft.md`
- **复审条件**：第 0 阶段发现纯整数和定点的生成方案做不到跨平台一致，或者精度不够

<a id="d-003"></a>
### D-003 数值精度属于规范名；第一阶段只测 R、T

状态：**已采纳** · 日期：2026-10-20

**背景**：v0.1 把数值精度算作离散化的一部分，§8.3 要求换数值精度复跑，可是规范只定义了一种精度，数据模型里精度又像是条目自己的参数。

**选项**：精度作为条目参数 / 精度属于规范名，换精度要用变体规范。

**决定及理由**：数值精度体现在规范名上，例如 lenia-q16 表示 16 位状态。条目的 `discretization` 只记 R 和 T。换数值精度复跑需要对应的变体规范（如 lenia-q12、lenia-q24），每个变体都要有自己的算法和测试向量，第一阶段做不完，所以第一阶段的离散化依赖测试只测 R、T。一个规范名对应一套确定的整数语义，测试向量和哈希才有意义。代价是：第一阶段的"柏拉图型 / 非柏拉图型"判断只覆盖 R、T 两个维度。建议在鉴定证书里写明测了哪些维度。

- **截止**：已定
- **拍板人**：创始人/制作人
- **影响的文档**：GDD §3.4(8)、§5.2、§8.3、§14.2(5)、§14.5；`spec/lenia-q16-draft.md`；鉴定规格 assay v1；种子悬赏规格（柏拉图型题目，见 D-007）
- **复审条件**：第二阶段开始前；或者有研究者需要精度维度的数据

<a id="d-004"></a>
### D-004 名称审核先于登记生效；属名来源与改属

状态：**已采纳** · 日期：2026-10-20

**背景**：v0.1 没有写清名称审核和命名仪式的先后，也没有写属名从哪里来；§8.5(8) 说"违规是名字可以被更改的唯一理由"，和系统分类修订导致的改属冲突。

**选项**：先登记、办仪式，再审核 / 先审核，通过后再登记。

**决定及理由**：描述提交后，名字先经过自动过滤和人工审核（暂定 24 小时内完成）。审核通过后登记才生效，触发命名仪式，进入 30 天异议期。优先权仍以描述提交时间为准（D-001），审核排队不会让人吃亏。命名仪式是全游戏情感的最高点（§13.1），不能先办仪式再撤名字。属名由描述者从已有的属中选择，或者提议一个新属，新属需要经过评审。系统分类修订导致改属时形成**新组合**：种加词和优先权保留，不算改名。这和生物命名法规的做法一致。

- **截止**：已定
- **拍板人**：创始人/制作人
- **影响的文档**：GDD §7、§8.5(4)(5)(8)、§13.1、§14.8；`naming-code-v0.md`；界面线框与首会话脚本
- **复审条件**：第一阶段的审核实际耗时远超 24 小时（暂定）；第一阶段由谁审核见 D-038

<a id="d-005"></a>
### D-005 描述配额对所有人相同

状态：**已采纳** · 日期：2026-10-20

**背景**：§3.2(6) 设了每人每周的描述配额，v0.1 没有说配额会不会随资历变化。

**选项**：所有人相同 / 随资历增加。

**决定及理由**：每人每周描述配额暂定 10 条，所有人相同。§3.3(7) 和 §9.4 说资历只解锁责任，不是数值；配额随资历增加，就成了数值上的特权，也让老玩家更容易抢占富矿。配额的作用是防止批量刷登记（§3.2(6)），并让每一次命名都被认真对待（§6），这两点对所有人都一样。

- **截止**：已定
- **拍板人**：创始人/制作人
- **影响的文档**：GDD §3.2(6)、§6；第一阶段 PRD；`naming-code-v0.md`
- **复审条件**：第一阶段数据显示配额总是用满、待描述库持续积压（§18.3），或者几乎没人用满。调整数字时对所有人同时生效

<a id="d-007"></a>
### D-007 第一阶段种子悬赏的选题范围；信号路由移到第二阶段

状态：**已采纳** · 日期：2026-10-20

**背景**：§3.1(2) 列了四个候选的种子悬赏。其中信号路由要把多个零件摆在一起并检查功能规格，需要第二阶段的构造能力。

**选项**：四个候选都可以选 / 第一阶段只从不需要构造能力的三个里选。

**决定及理由**：信号路由移到第二阶段，作为构造玩法的长期目标（§9.2）。第一阶段的 1–2 个种子悬赏从其余三个里选：**抗碰撞的移动体**、**柏拉图型与非柏拉图型**、**相图的普适性**。抗碰撞的判定器可以让一个物种和它自己的副本相撞，在参考实现上自动运行，不需要对撞台。柏拉图型题目在第一阶段只能覆盖 R、T 维度（D-003）。最终选题在研究者访谈之后与顾问一起定。这些候选题的依据都是近两年的论文，其中 Gupta（2026）的预印本我们只读过二手摘要，Hudcová 等（2026）只读过两页摘要，写进悬赏之前要先核对原文。

- **截止**：已定（具体选题在第一阶段开始前，见种子悬赏规格）
- **拍板人**：创始人/制作人
- **影响的文档**：GDD §3.1(2)、§9.2、§9.3；`research/interview-plan.md`；种子悬赏规格与研究者合作协议
- **复审条件**：访谈显示研究者更需要别的问题

### D-018 数据许可（§22(6)）

状态：**提议** · 日期：2026-10-20

**背景**：§14.9 建议图鉴数据用 CC0，描述文字和图版用 CC BY 4.0，标的是"建议"，§22(6) 仍未决定。[致 Chan 的许可请求](./outreach/chan-permission-request.en.md)会把"当前方案"告诉对方，所以发信之前必须先定方向。Chan 的 Lenia 代码以 MIT 许可开源，但物种数据能否以 CC0 再发布并没有确定，这正是许可请求要问的。数据一旦以某种许可发布就不能收回。

**选项**：

| 选项 | 好处 | 代价 |
|---|---|---|
| A 数据 CC0，文字和图版 CC BY 4.0（GDD 默认） | 研究者再利用没有门槛（Wikidata 也用 CC0）；署名靠共同体规范和引用机制 | 无法用许可强制署名 |
| B 全部 CC BY 4.0 | 署名有法律保障 | 所有数据的再利用门槛都提高；大规模合并数据时署名负担重 |
| A′ 在 A 的基础上，来自 Chan 工作的文献条目按对方意愿单独用 CC BY 4.0 | 尊重原作者，又不改变整本图鉴 | 图鉴变成混合许可，导出要按条目标许可（§14.5 已有 `license` 字段） |

<a id="d-021"></a>
### D-021 哈希算法：SHA-256 还是 BLAKE3

状态：**提议** · 日期：2026-10-20

**背景**：内容寻址的状态存储（§14.1）、采集和描述承诺（D-001）、轨迹指纹（§14.2(4)）、核与查找表的哈希（D-002）都需要一种哈希算法。它一旦写进测试向量和证书，就只能在新版本规范里更换。§14.5 的草案用的是 `sha256:` 前缀。

**选项**：

| 选项 | 好处 | 代价 |
|---|---|---|
| SHA-256 | 标准化（FIPS 180-4）；几乎所有语言都内置，浏览器的 WebCrypto 也内置；第三方最容易独立核对 | 比 BLAKE3 慢 |
| BLAKE3 | 很快，支持并行和树形哈希 | 浏览器没有内置，要另带库；不是 NIST 标准算法，几十年后的可得性略弱 |

**建议（尚未拍板）**：SHA-256。速度不是瓶颈：一张 256×256 的 16 位状态只有 128 KiB，而且每 256 步才算一次。长期可复核（§14.9 的"公司倒闭演练"）比速度重要。所有哈希字符串都带算法前缀（如 `sha256:`），将来的规范版本换算法也不会产生歧义。哈希的输入是规范序列化之后的字节（D-026）。

- **截止**：第 2 周
- **拍板人**：后端与数据工程师
- **影响的文档**：`spec/lenia-q16-draft.md`；数据模型与导出格式；`naming-code-v0.md`（承诺的构造）
- **复审条件**：SHA-256 出现可实际利用的碰撞攻击。届时在新版本规范里增加算法，旧条目不变

<a id="d-022"></a>
### D-022 确定性 exp 与定点数学方案

状态：**提议** · 日期：2026-10-20

**背景**：核心函数 K_C(r) = exp(α − α/(4r(1−r))) 和生长函数 G(u) = 2exp(−(u−μ)²/(2σ²)) − 1 都要算 exp（附录 A）。D-002 规定核和查找表由规范算法生成，§5.4 规定只用整数和定点运算。各平台浮点 exp 的实现结果不同，不能直接用。

**选项**：

| 选项 | 好处 | 代价 |
|---|---|---|
| A 纯定点 exp：规范正文写出完整算法（区间约简加多项式或查表）和全部常数 | 第三方只看规范就能实现；符合 §5.4 | 要自己分析误差上界；工作量最大 |
| B 钉死某个版本的软件数学库 | 实现快 | 规范要引用外部代码，用别的语言的第三方很难逐位复现；库停止维护时有风险 |
| C 生成阶段允许用 float64 的基本运算自写 exp | IEEE 754 规定基本运算正确舍入，原则上可以跨平台一致 | 与 §5.4"只用整数和定点运算"不符，要改 GDD；第三方要防编译器优化改变运算 |

**建议（尚未拍板）**：A。另外用任意精度计算得到离线参考值，只用来检验定点结果的误差，不进入规范语义。第 1–2 周的跨平台确定性测试不必等本条：可以先在一台机器上生成核和查找表，作为文件分发到其他平台，只比对演化本身。

- **截止**：第 3 周
- **拍板人**：后端与数据工程师
- **影响的文档**：GDD 附录 A；`spec/lenia-q16-draft.md`；参考实现原型
- **复审条件**：定点误差在某些参数区域（例如 σ 很小时）明显改变物种行为

<a id="d-023"></a>
### D-023 NTT 模数与直接求和的切换

状态：**提议** · 日期：2026-10-20

**背景**：§14.2(1) 规定半径小时直接求和，半径大时用数论变换（NTT），两种算法的结果逐位相同。附录 A 的设计保证累加和小于 2^32（65535 × 2^16 < 2^32）。

**关键一点**：两种算法算的是同一个精确的整数卷积，切换点只影响速度，不影响结果。所以规范只需要定义"环面上的精确整数循环卷积"，NTT 模数和切换阈值属于参考实现的选择，不写进规范语义。

**选项（模数）**：

| 选项 | 好处 | 代价 |
|---|---|---|
| A 一个大于 2^32 的 NTT 友好素数，例如 2^64 − 2^32 + 1 | 一次变换；支持很长的二次幂长度 | 乘法需要 128 位中间结果，WASM 里要软件模拟，较慢 |
| B 两个约 30 位的素数加中国剩余定理，例如 998244353 = 119·2^23 + 1 和 754974721 = 45·2^24 + 1，乘积约 7.5 × 10^17，大于 2^32 | 只用 64 位运算，对 WASM 友好 | 要做两次变换；实现稍复杂 |
| C 不用 NTT，只用直接求和 | 最简单 | 每格的乘加次数随 R² 增长，大半径时慢 |

**建议（尚未拍板）**：第 3 周按实测速度在 A、B 里选，倾向 B。环面尺寸取 2 的幂（与 D-025 联动），NTT 长度就不用另做处理。切换阈值按实测定，写进参考实现的文档，不写进规范。测试要求两种算法在所有测试向量上逐位相同。WebGPU 上的精确路径只做直接求和（§14.2(2)）。

- **截止**：第 3 周
- **拍板人**：后端与数据工程师
- **影响的文档**：GDD §14.2、§14.3；`spec/lenia-q16-draft.md`（只写卷积语义）；参考实现原型
- **复审条件**：实测的鉴定成本远高于 §14.3 的粗估

<a id="d-024"></a>
### D-024 参数的定点编码与合法格点

状态：**提议** · 日期：2026-10-20

**背景**：D-002 规定参数用定点编码，具体怎么编没定。§8.4(5) 用"规则点相同"判同种，而规则点按规范的参数格点判定。条目编码、查重、分享链接和测绘都依赖它，规范冻结后不能再改。文献参数多是十进制小数，例如 Orbium 的 μ = 0.15，σ 约为 0.015（有的来源写 0.014）。

**选项**：

| 选项 | 好处 | 代价 |
|---|---|---|
| A 十进制定点：μ、σ 存为整数 × 10^−k | 文献里的十进制参数能精确表示；界面输入直观 | 换算到内部定点运算时要规定取整 |
| B 二进制定点：μ、σ 存为整数 × 2^−k | 与内部运算对齐 | 0.15 这样的值不能精确表示，文献参数只能取近似 |

**建议（尚未拍板）**：A。

- μ、σ 的步长暂定 0.0001。
- β 用分母较小的有理数表示。Chan 的数据里 β 常写成分数 [verify]，分母上限在核对 Chan 物种数据的格式之后定。
- R、T 为正整数。第一阶段的取值范围暂不定，R 的上限与核权重精度（D-028）一起定。
- 核函数族、生长函数族用规范里的枚举名。
- **同一规则点**＝规范版本相同，且所有编码后的整数完全相同。
- 控制台"微调"模式的最小步长等于格点步长。

步长的取舍：格点越细，同一个种出现在相邻格点上的情况越多。相邻格点上的同一个种不会被自动判同，只能靠连续性检验或评审，评审量会变大。格点越粗，越可能漏掉只在很窄的参数区间里存在的种。第 3 周用 Orbium 等物种实测，看相邻格点上的行为是否明显变化，再确认步长。

- **截止**：第 2 周定编码形式；第 3 周实测后确认步长
- **拍板人**：后端与数据工程师
- **影响的文档**：GDD §5.4、§8.1、§8.4(5)、§14.5；`spec/lenia-q16-draft.md`；数据模型；查重与评审规格 dedup v1
- **复审条件**：导入文献物种时发现大量参数落不到格点上

<a id="d-025"></a>
### D-025 环面尺寸属于规范还是鉴定协议

状态：**提议** · 日期：2026-10-20

**背景**：§5.4 已经规定边界是环面，§20 规定鉴定用的世界尺寸由规范固定（D-012）。还没定的是：具体尺寸是多少；是一个尺寸还是一组尺寸；尺寸记在哪里。§14.3 写"128×128 到 256×256 的窗口"，§14.5 的模式标本有 `window` 字段。局域性、扩张体判定和繁殖率都和尺寸有关：扩张体或辐射体在小环面上会绕回来撞上自己。

**选项**：

| 选项 | 好处 | 代价 |
|---|---|---|
| A 规范规定一个固定尺寸，所有鉴定都在这个尺寸上跑 | 最简单；条目之间可比 | 大生物和扩张体放不下；小生物浪费算力 |
| B 规范规定一组合法尺寸，模式标本记录自己所在的尺寸，鉴定协议规定怎样选尺寸 | 兼顾成本和大生物 | 同一个种在不同尺寸上的轨迹哈希不同，要写清楚以哪个为准 |
| C 尺寸只属于鉴定协议，规范不管 | 灵活 | 与 §20 冲突；同一条目在不同尺寸上复现的结果不同，"一条链接逐位复现"失去意义 |

**建议（尚未拍板）**：B。合法尺寸取 2 的幂，暂定 128 和 256（与 D-023 联动）。环面尺寸属于模式标本：成体快照的尺寸就是环面尺寸，§14.5 的 `window` 按此注明。鉴定协议规定取能容纳成体并留出边距（暂定）的最小合法尺寸；局域性和扩张的判定要在更大的合法尺寸上再跑一次，排除环面绕回造成的假象。

- **截止**：第 2 周
- **拍板人**：后端与数据工程师
- **影响的文档**：GDD §5.4、§8.2、§8.3、§14.3、§14.5、§20；`spec/lenia-q16-draft.md`；鉴定规格 assay v1；数据模型
- **复审条件**：出现在最大合法尺寸里也放不下的稳定生物

### D-026 状态与参数的规范序列化格式

状态：**提议** · 日期：2026-10-20

**背景**：哈希（D-021）、内容寻址存储（§14.1）、分享链接（§14.4）和承诺（D-001）都要求同一个状态、同一组参数在任何实现里得到完全相同的字节。

**选项**：

| 选项 | 好处 | 代价 |
|---|---|---|
| A 定长头（格式标识、规范版本、宽、高）加行优先、小端序的 16 位原始数据 | 简单，任何语言都能写 | 体积大，传输时要另外压缩 |

- **截止**：第 2 周
- **拍板人**：后端与数据工程师
- **影响的文档**：`spec/lenia-q16-draft.md`；数据模型与导出格式；系统架构与接口契约
- **复审条件**：多通道 Lenia 的规范需要新格式。届时随新规范发新格式，不改旧格式

<a id="d-027"></a>
### D-027 规范正文与参考实现冲突时以谁为准；出 bug 后已签发证书怎么处理

状态：**提议** · 日期：2026-10-20

**背景**：§5.4 规定"宇宙不打补丁，只发新版本"，§14.2(6) 规定参考实现的每个版本永久归档。但 GDD 没有写：规范正文和参考实现不一致时以谁为准；参考实现或鉴定套件有 bug 时，已签发的证书怎么办。第一次修 bug 时就会遇到这个问题。要分清两类问题：**宇宙语义**的不一致（实现算出的下一步状态和正文不同），和**鉴定测量**的 bug（周期、对称、类别算错了）。

**选项**：

| 选项 | 好处 | 代价 |
|---|---|---|
| A 正文为准：实现改成正文的样子，已登记条目重新鉴定，不再存活的撤回 | 规范文本干净 | 已登记的种可能消失，违背"永久成立" |
| B 已归档的参考实现为准：给正文发勘误，把实现的实际行为写清楚 | 条目永不受影响 | 规范里会留下"怪癖"，第三方实现要连怪癖一起实现 |
| C 分阶段处理（见下） | 保住永久性，也留出修正的途径 | 规则稍复杂 |

**建议（尚未拍板）**：C。

1. **规范**＝规范正文加上随规范发布的测试向量。
2. **冻结之前**：发现冲突就改错的那一方。
3. **冻结之后，宇宙语义冲突**：如果已归档参考实现的行为是确定的、跨平台一致的，就以它为准，给正文发勘误。宇宙不变，条目不受影响。如果这个行为不理想，在新版本规范里改。
4. **实现的行为本身不确定**（例如跨平台不一致）：它不定义任何宇宙，受影响的条目按正文重新鉴定。
5. **鉴定测量的 bug**：不改变宇宙。修好鉴定套件，重新签发受影响的证书，旧证书保留并标"已更正"。如果更正后条目不再满足登记条件（例如其实没有存活），走 §15 的撤回与更正流程，编号保留，状态改为 `withdrawn`（§14.5）。

- **截止**：第 2 周定原则，写进规范草案；证书处理细则在第一条登记之前定
- **拍板人**：创始人/制作人（涉及对玩家和研究者的永久性承诺）

### D-028 16 位精度的结论（来自第 0 阶段实测）

状态：**提议** · 日期：2026-10-20

**背景**：§14.2 把它列为第 0 阶段的验证项：16 位状态和 2^16 的核权重精度够不够用，不够就用双 u32 模拟 64 位累加。改用双 u32 会改变附录 A 的公式和 WebGPU 上的精确路径，所以结论必须在规范 v1.0 冻结之前得出。

粗算（指数型核心函数，α = 4）：核权重总和固定为 2^16 时，R 越大，每格分到的权重越小。R = 13 时，最大的单格权重约 320；R = 50 时只有约 22，并且近一半格子的权重小于 5，取整误差相对变大，核的形状会失真。所以**精度问题和第一阶段允许的 R 范围是同一个问题**。

**选项**：

| 选项 | 好处 | 代价 |
|---|---|---|
| A 保持 16 位状态、2^16 核权重、u32 累加（GDD 草案） | 最简单；WebGPU 精确路径可用 | 大 R 时核的形状失真 |
| B 16 位状态，核权重精度提高，双 u32 模拟 64 位累加 | 大 R 时精度足够 | 附录 A 和 WebGPU 精确路径要改；速度变慢（幅度待实测） |
| C A 加上第一阶段的 R 上限，大 R 留给以后的变体规范 | 不改架构 | 第一阶段的规则空间变小；离散化测试能用的 R 范围受限 |

**建议（尚未拍板）**：第 2–3 周实测：整数版和 float64 版在约 10 个经典物种上对比存活、速度和周期，判据按[第 0 阶段执行计划](./phase0-plan.md)。第 4 周评审时定。如果在第一阶段需要的 R 范围内 A 已经够用，就选 C；不够才选 B。结论和数据一起写进本条。

- **截止**：第 4 周；最晚在宇宙规范 v1.0 冻结之前
- **拍板人**：后端与数据工程师（创始人确认）
- **影响的文档**：GDD §14.2、附录 A；`spec/lenia-q16-draft.md`；D-024（R 的范围）；D-033
- **复审条件**：研究者或悬赏需要更大的 R

### D-029 显微镜默认浮点还是整数；浮点"幻影生物"怎么处理

状态：**提议** · 日期：2026-10-20

**背景**：§8.1 和 §14.2(2) 规定显微镜用 GPU 浮点快速预览，整数实现用于精确复现；WebGPU 上也能跑逐位精确的直接求和。在浮点预览里活着、在 lenia-q16 里却活不下去的结构，这里叫**幻影生物**。如果它被采集或展示成物种，就碰到了红线 1"不伪造发现"。

**选项**：

| 选项 | 好处 | 代价 |
|---|---|---|
| A 默认浮点预览（GDD 现状），采集时用整数实现复核 | 最快最流畅 | 会出现幻影，玩家可能空欢喜 |
| B 默认整数精确（WebGPU 直接求和或 WASM） | 看到的就是真实的 | 大 R 时慢；精确路径的工程量 |
| C 浮点计算，但每步把状态量化到 16 位 | 可能缩小和整数版的差距 | 仍然不逐位一致，效果要实测 |

**建议（尚未拍板）**：第一阶段保留 A 作为默认，加三条规则：

1. 采集箱预检（§8.2）一律用整数实现从成体快照复跑。在整数版里活不下去的候选标为"只在浮点预览中出现"，不能送检，不能登记，不进观察志。
2. 界面如实说明原因，不把它展示成物种。
3. 提供"精确模式"开关，R 较小时用 WebGPU 精确路径。

第 3 周用最小探索器测幻影率。第 4 周评审时，如果幻影率高（阈值暂定，在第 0 阶段执行计划里定），默认改为 B 或 C。

- **影响的文档**：GDD §8.1、§8.2、§14.2(2)、§14.7；采集交接规格；客户端性能、回退与光敏安全规格；界面线框

**背景**：§14.2(2) 已经定了参考实现用 Rust，同一份代码编译成服务器原生程序和 WebAssembly，WebGPU 路径用 WGSL 另写。第 0 阶段第 1 周就要建仓、写原型，在三种平台上比对哈希。

**选项与建议（尚未拍板）**：

| 项目 | 选项 | 建议 |
|---|---|---|
| 仓库结构 | 单仓 / 多仓 | 单仓，分 spec/、ref/（Rust）、web/、docs/，规范和实现一起改 |
| Rust 版本 | 跟随最新稳定版 / 钉死版本 | 用工具链文件钉死版本；升级前跑完全部测试向量 |
| WASM 构建 | 是否启用 SIMD、线程 | 可以用普通的整数 SIMD；禁用 relaxed SIMD，它允许不同实现给出不同结果；第一阶段不用线程，线程需要跨源隔离，会妨碍 §14.4 的嵌入代码。参考实现核心不用浮点运算，CI 里扫描 WASM 产物，确认没有浮点指令 |
| CI | 托管 CI（如 GitHub Actions）/ 自建 | 托管 CI。矩阵至少三种平台（暂定 Linux x86-64、macOS ARM64、Windows x86-64），每次提交比对测试向量的哈希；另用无头浏览器跑 WASM 版 |
| 前端框架 | 无框架（TypeScript 加 Vite）/ React / Svelte 等 | TypeScript 加 Vite；界面框架选到岗工程师最熟的。影响小，第一阶段开工前还可以换 |
| WebGPU 封装 | 直接用 WebGPU API / three.js 等库 / Rust 的 wgpu 编译到 WASM | 直接用 WebGPU API 加一层薄封装：预览主要是计算着色器，渲染只是一张纹理。WebGL2 回退见 §14.7 |

- **截止**：第 1 周
- **拍板人**：后端与数据工程师（参考实现与 CI）；模拟与图形工程师（前端与 WebGPU）。到岗之前由创始人兼
- **影响的文档**：GDD §14.1、§14.2、§14.7；[第 0 阶段执行计划](./phase0-plan.md)；系统架构与接口契约
- **复审条件**：到岗工程师提出异议；某个平台上出现不一致

### D-038 第一阶段的临时评审与裁决人

### D-039 0 级同意的边界：慧眼标记、起点引用与运营遥测

状态：**提议** · 日期：2026-10-20

**背景**：v0.2 的 §11.2 已经写明：已采集标本的探索路径属于登记必需的出处，停留、跳过、放大查看属于好奇心数据（D-012）。还没写清的有三件事：慧眼标记（§3.2(3)）在 0 级同意下是否保留；起点引用（§9.4）依赖的探索路径，在什么情况下算出处；运营遥测（崩溃报告、性能数据、§18.1 回访率需要的登录记录）是否受分级同意约束。

**选项**：每一项都可以归入"登记必需的出处"（0 级也保留），或归入"好奇心数据"（1 级以上才记录）。

**建议（尚未拍板）**：

- **慧眼标记**是玩家为了记功而主动提交的动作，0 级下也保留，但只用于记功；只有 1 级以上同意，才用于训练有趣性模型。
- **起点引用**：只有最终采集到新物种时，从起点到采集的那段路径才作为出处保留。
- **运营遥测**与好奇心数据分开：只收集运行所必需的最少数据，在隐私政策里单独列出，不进入任何研究数据集。

- **截止**：第一阶段开始前
- **拍板人**：创始人/制作人
- **影响的文档**：GDD §3.2(3)、§9.4、§11.2、§18；隐私政策与同意流程；遥测与指标口径；采集交接规格
- **复审条件**：伦理审查（D-036）要求不同的边界
